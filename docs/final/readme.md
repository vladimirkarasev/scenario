# Сравнение текущей версии сценария и нового механизма сценариев

Администратор — пользователь, который создает и настраивает сценарии.
Оператор — пользователь, который проходит сценарии и работает с ними.

## Главные фишки нового механизма сценариев

- У сценария, справочника есть версии, что позволяет иметь черновою версию, и только после тестирования опроса его можно
  опубликовывать операторам. Почему это важно, в одной из интеграций приходилось править на живую, когда операторы
  работали.
- Все поля разбиты на специализированные (email, phone, text, number, textarea, ....) поля, в текущей версии сценария
  это нет, поэтому есть такие
  кейсы когда операторы вводили email с ошибкой например: в email@yandex.ru оператор вместо x - латиницей ввел
  кириллицей, текущая версия сценария ошибку не выдало, но при отправке в crm заказчика валидация случилась и лид не
  создался.
- Отложенная обработка нескольких action chain/batch с возможностью backoff. Для отложенной обработки используются
  temporal.
- Action можно запустить и не ждать его ответа — оператор сразу идёт дальше по опросу, а action отрабатывает в фоне.
  В текущей версии оператор фактически ждёт, пока улетит письмо или лид в CRM, прежде чем перейти к следующему
  клиенту — тут это не нужно, опрос проходит быстрее просто за счёт того, что не ждём.
- skills для codex и claude, чтобы можно было бы быстро внедрять интеграции и новые поля.
- модульная архитектура, есть вдруг модуль понадобиться для другого проекта можно его вытащить, или если модуль
  покажется что он перерос с сервис его можно вынести.
- Справочник - это отдельный модуль справочника и динамическими полями фильтрацией и типами справочника. обычный, excel,
  api, external
- У action, справочника, proxy и сценария есть общий каталог с категориями — не переизобретал под каждый раздел свою
  систему папок/поиска, один и тот же механизм используется везде.
- Ошибки по API/интеграциям видно прямо в интерфейсе — есть страница с историей запросов (что ушло, что вернулось,
  какой статус), и у каждого запроса есть свой request_id, который тянется через всю цепочку обработки. Раньше на поиск
  причины ошибки уходило много времени именно потому что не понятно куда смотреть — теперь просто открываешь конкретный
  запрос и видишь, что там было.
- есть отдельная страница для просмотра сценария

## Текущая версия: плюсы и минусы

**Плюсы**

- стабильная работа и уже обкатанные решения

**Минусы**

- Количество репозиториев сейчас значительно усложняет поддержку. Например, для добавления списка обращений приходится
  вносить изменения сразу в несколько проектов: реализовывать CRUD в scenario-builder, добавлять проксирование в VER,
  создавать новое action и добавлять справочник в dictionary в репозиторий scenario-action, в gojs добавить серверную
  фильтрацию. При этом, как мне сказали, набор полей у разных линий может отличаться, из-за чего реализация и дальнейшая
  поддержка становятся ещё сложнее. Также для работы над проектом нужно эти 4 репозитория развернуть и запустить.
- Есть еще отдельный проект для ver - если вдруг он появиться, то это будет 5 репозиторий в копилку
- Много копипаста: одна и таже интеграция может быть написана заново.
- Много классов полей в scenario-action которые не нужны и сложно читаемы
- Логирование ошибок оставляет желать лучшее, сейчас иногда на то чтобы, найти лог уходит много времени, потому-что нет
  стандартизации по логам и каждый кто работал над проектом, внес свою лепту по логам
- frontend - тут все печально, есть в старом стиле vue часть в новом где-то js где-то ts. Это еще я молчу по качеству
  кода и переиспользования компонентов
- Справочники. По факту справочники в основном это обертка над api/excel заказчика. Иногда api отваливаются или
  загружаются долго, я в некоторых справочнике сделал кэширование и прогрев кэша, чтобы как-то ускорить работу. Но это
  все равно такое себе решение и редактирования справочника только руками разработчика
- нет специализированных полей, например email, phone, vin, grz валидация полей происходит за счет regexp который не
  должен знать администратор, да есть подсказки, но все же

## Новая версия: плюсы и минусы

**Минусы**

- нет стабильной версии, нужно протестировать + обкатывать решения
- ui в некоторых местах не доработан.
- нет всех справочников и интеграция, которые есть в текущем справочнике.

**Плюсы**

- 1 репозиторий
- модульность в backend и фронтенд, все разнесено по модулям
- websocket - в проекте
- Справочник можно наполнить четырьмя способами: вбить вручную, загрузить excel файлом, подключить к внешней системе с
  периодическим обновлением (данные сохраняются и обновляются по расписанию) или подключить «напрямую» — когда данные,
  берутся из внешней системы прямо в момент запроса.
- обработка шагов справочника в 1 месте и на backend с использованием пакета symfony/expression-language, это позволит в
  будущем применять сценарий, например: телеграм ботов, shared опросы как например коллеги из hr присылают опросы
  сотрудников.
- версии справочников/сценариев
- в сценариях поля конкретные например: vin, phone, text, email, grz, suggest
- для локальной разработки добавил buggregator.
- openapi - документация
- логирование и тестирование unit, e2e, future. e2e - только на критически важные функции, например: создание опроса,
  обход по опросу
- для правок в большинстве случаев не нужен ver
- skills для ai инструментов, что существенно ускоряют разработку
- модуль proxy - нужен только для создания api. в ui можем добавить несколько интеграций к api. например есть заказчик,
  который использует одну и туже crm, только с разными доступами в этом модуле достаточно api и подключить интеграцию с
  доступами в ui и все. 10-20 минут работы.
- ui более удобная для пользователей
- action - он будет использовать модуль proxy с полями которые есть у proxy.
- Единый каталог категорий — сразу для сценариев, action, proxy и справочников.
- Логи/ошибки по API смотрятся прямо в UI, с request_id на всю цепочку запроса — не нужно просить разработчика лезть в
  серверные логи, чтобы понять, что сломалось.
- Отдельная нода для action (не поле внутри шага, как раньше) — можно гонять несколько action параллельно или строго по
  очереди, в зависимости от того, важен порядок или нет, плюс не ждать ответа и не блокировать оператора (см. фишки
  выше).
- поддерживать проект можно только в 1 репозитории.

## Резуме

Изначально была цель изучить новые технологии и попробовать разработку с 0 с использование ии, но видимо я зашел слишком
далеко) что новый механизм сценариев получился интересным и его хочется показать.
С ее помощью можно существенно сократить время работы операторов, администраторов, разработчиков и также улучшить
качество и удобство создания и прохождения опросов.

Разработчики - не будут выполнять однотипные задачи, например: добавление очередного одинакового справочника, изменение
сортировки колонок, добавление фильтров, даже добавление action. Базово, планируется, просто делать proxy, а через ui
будет он подключаться к action и справочнику - все. Плюс меньше времени будет уходить на поиск багов в интеграциях —
ошибки и request_id видно сразу в интерфейсе, не нужно лезть в логи вручную.

Администраторам - больше контроля, быстрота внесения правок, безопасное добавление и проверка сценариев/опросов. по ui
очень много изменения, я их пытался сделать понятными и доступными. Например: переменные вынесении в отдельный блок с
подсказками, добавляем правочник и него досупна подсказка какие поля там вообще существую и какие можно использовать.

Операторы - нет ненужных им блоков, по типу отправка email. Ведь оператору не важно в какую crm и куда идут результаты
опроса ему важно пройтись и заполнить опрос со слов клиента. Качество и простота выполнения опроса, например: была
проблема с фио) в одном и тоже опросе только в разных ветках нужно только имя в другой ветке полностью фио, в своем
справочнике я подключил подсказку от dadata и все, теперь получаю распаршеное фио, а операторам удобство заполнения.

Также мы можем выйграть очень много времени, т.к. теперь над созданием новой интеграции для опроса можно работать
параллельно с администратором, в новом механизме сценариев предусмотрены mock-ответы.

Также есть планы по внедрению картографии и ai для операторов.

## Целесообразность для компании

Да, мы можем доработать текущую версию и внедрить туда всё, что я описал выше. Но на это уйдёт очень много времени, и
не факт, что это в итоге сократит время на внедрение новых функций — потому что проблема больше архитектурная: она в
том, что система разбита на 4 отдельных репозитория. Доработки приходится
тянуть сразу через несколько проектов, и это никуда не денется, даже если перенести в старую систему часть улучшений
из нового механизма сценариев.

Сейчас над сценариями работает всего один разработчик, и тащить доработку по 4 репозиториям одновременно — очень сложно
и трудозатратно.

Я думаю, что сейчас нужно действовать в сторону упрощения и оптимизации времени — причём не только времени
операторов, но и времени разработки. Поэтому переход на новый механизм сценариев сейчас — да, будет затратным, но дальше на
поддержку и на новые интеграции будет уходить значительно меньше времени, чем сейчас.

Например, коллеги закладывают на одну интеграцию порядка 6 месяцев — на мой взгляд это очень много. Да, там есть время
на
согласования и обсуждения, не только на код, но даже с учётом этого срок кажется слишком большим. На последней задаче
внедрения мы потратили порядка 3 недель на интеграцию, а она простая, 4 - справочника, 2 - action создание лида в crm,
потом автоматическое закрытие лида. Идеального времени примерно 2 - 2.5 недели - это когда 8 часов, без созвонов и
отвлечений на другие задачи. На мой взгдял в новом механизме сценариев с ии можно сделать за несколько дней, и то время с большим запасом.
Когда внедрял dadata, ии дал задание он, сделал это за 15 - 20 минут + рефакторинг 1 час. подключение через ui 20 минут,
взял все методы) которые там есть.

Ещё один плюс нового механизма сценариев — онбординг нового разработчика: он может быстрее влиться в проект и уже
выполнять задачи, например по написанию api-интеграций. Плюс в новом механизме сценариев я хочу сделать подробную
документацию — не только для
программистов, но и для всех остальных, кто будет с этим работать.

## План перехода

1. Тестирование и очень много ручного тестирования, на stage.
2. Текущий проект замораживаем - переводим в режим "только поддержка", новые функции туда больше не пишем.
3. На переходный период текущие опросы продолжают открываться внутри новой системы через iframe -
   для пользователя это выглядит бесшовно, он не замечает разницы.
4. Все новые опросы сразу создаются в новой системе.
5. Текущие опросы переносим по одному: сначала mapper/конвертер, потом **ручная проверка**, и только после
   проверки - переключение на новую версию.
6. Справочники и action переносятся - там риски минимальны.

Также для переноса точно будет использоваться ии что существенно сократит время на перенос. Прикрепил к архиву еще
скрины ui.
