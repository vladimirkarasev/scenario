# Architecture Audit

Работать от измеримого baseline к небольшим проверяемым изменениям. Сохранять пользовательские изменения в dirty worktree и не менять поведение без отдельного запроса.

## Границы аудита

- Инвентаризировать каждый каталог `module/*` и `resources/js/modules/*`; не считать выборочную проверку аудитом всех модулей.
- Классифицировать находки по риску и исправлять сначала service locator, бизнес-логику в transport/UI слоях, циклические зависимости, небезопасные данные и гонки.
- Проверять SOLID по наблюдаемым обязанностям и направлениям зависимостей. Не требовать интерфейс для каждого класса и не дробить связную логику ради размера файла.
- Применять GoF только при реальной вариативности: Strategy для заменяемого поведения, Factory для создания вариантов, Adapter для внешних контрактов, Repository для persistence/HTTP, Composite для деревьев и Command для явных мутаций.

## Backend

Дополнительно применять `laravel-refactor` и проектные API/test skills по их trigger rules.

- В `module/*` запрещены `app()`, `resolve()` и `request()`. Request передавать параметром контроллера, зависимости — через constructor DI.
- Service provider является composition root: допустим `$this->app->bind()`/`make()` для регистрации, но не global container helpers.
- Контроллеры не выполняют запросы к БД и доменные мутации напрямую; модели не разрешают сервисы из контейнера.
- Реестры и фабрики получают стратегии через DI и не скрывают container lookup внутри `make()`/`resolve()`.

## Frontend

Дополнительно применять `frontend-audit` и `vue-refactor`.

- Page/component отвечает за composition и rendering; orchestration живёт в composable, HTTP и normalization — в repository, публичные типы и схемы — в своих каталогах.
- Для конкурентных reads использовать общую latest-wins policy; mutations не отбрасывать.
- Не вводить абстракцию без устойчивой границы или второго варианта поведения.

## Проверка

Запускать проверки только через Taskfile согласно `test-with-taskfile`. Минимум: полный PHPStan, TypeScript, ESLint без errors, релевантные тесты и `git diff --check`. Для module-wide frontend изменений также production build.

В итоговом отчёте перечислить каждый модуль как проверенный, исправленный или оставшийся с конкретным риском. Не заявлять полное соблюдение SOLID/GoF, если остались неисследованные модули.
